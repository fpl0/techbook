# Simulating a Thompson NFA in linear time, and what production engines do

Research notes for "A Regex Engine From Scratch". Format: claim — URL — quote/section. Access date for all sources: 2026-09-05. Quotes are verbatim from the page text as fetched on that date.

## 1. Thompson/Pike simulation and the O(n·m) bound

- **Core idea: be in many states at once.** Cox 2007, section "Regular Expression Search Algorithms": "A more efficient but more complicated way to simulate perfect guessing is to guess both options simultaneously. In this approach, the simulation allows the machine to be in multiple states at once. To process each letter, it advances all the states along all the arrows that match the letter." — https://swtch.com/~rsc/regexp/regexp1.html
- **Epsilon closure at the start (and after every step).** Same section: "The machine starts in the start state and all the states reachable from the start state by unlabeled arrows." In Cox's C code the closure is done eagerly inside `addstate`: "Addstate also follows unlabeled arrows: if s is a Split state with two unlabeled arrows to new states, addstate adds those states to the list instead of s." (section "Implementation: Simulating the NFA") — same URL.
- **Why it is linear.** Same section: "In the worst case, the NFA might be in every state at each step, but this results in at worst a constant amount of work independent of the length of the string, so arbitrarily large input strings can be processed in linear time. This is a dramatic improvement over the exponential time required by the backtracking approach." — same URL.
- **Exact bound.** Cox 2007, section "Performance": "Thompson's algorithm maintains state lists of length approximately n and processes the string, also of length n, for a total of O(n2) time. (The run time is superlinear, because we are not keeping the regular expression constant as the input grows. For a regular expression of length m run on text of length n, the Thompson NFA requires O(mn) time.)" — same URL.
- **Bound and memory, VM formulation.** Cox 2009, "Thompson's Implementation": "If addthread does not add a thread to the list if an identical thread (with the same pc) is already on the list, then ThreadLists only need room for n possible threads, eliminating the possibility of overflow. Having at most n threads on a list also bounds the amount of time spent processing each character. Assuming an efficient O(1) implementation of addthread, the worst case time for processing a single character is only O(n), so the time for the entire string is O(n m)." Cox swaps letters between articles: in 2009, n = program size, m = input length. Memory: two lists of at most program-size entries plus the compiled program. — https://swtch.com/~rsc/regexp/regexp2.html
- **The benchmark.** Cox 2007, "Introduction" and "Performance": input family is the pattern `a?^n a^n` matched against the string `a^n` ("Let's use superscripts to denote string repetition, so that a?3a3 is shorthand for a?a?a?aaa. The two graphs plot the time required by each approach to match the regular expression a?nan against the string an."). Numbers reported: "Notice that Perl requires over sixty seconds to match a 29-character string. The other approach, labeled Thompson NFA for reasons that will be explained later, requires twenty microseconds to match the string. That's not a typo. The Perl graph plots time in seconds, while the Thompson NFA graph plots time in microseconds: the Thompson NFA implementation is a million times faster than Perl when running on a miniscule 29-character string. The trends shown in the graph continue: the Thompson NFA handles a 100-character string in under 200 microseconds, while Perl would require over 10^15 years." (The 10^15 figure is an extrapolation, not a measurement; Cox says "would require".) — regexp1.html
- **Why backtracking is exponential on this input.** "Backtracking regular expression implementations implement the zero-or-one ? by first trying one and then zero. There are n such choices to make, a total of 2^n possibilities. Only the very last possibility—choosing zero for all the ?—will lead to a match. The backtracking approach thus requires O(2^n) time, so it will not scale much beyond n=25." — regexp1.html, "Performance"
- **Second graph, other engines.** "From the graph it is clear that Perl, PCRE, Python, and Ruby are all using recursive backtracking. PCRE stops getting the right answer at n=23, because it aborts the recursive backtracking after a maximum number of steps." "Awk, Tcl, GNU grep, and GNU awk build DFAs". — regexp1.html, "Performance"
- **Conditions of the measurement.** The article text does not state the CPU, OS, or Perl version used for the graphs (grepped for machine/GHz/Perl 5.x: nothing). Cox notes the C implementation "was not written with performance in mind." Treat the numbers as 2007-era, machine-unspecified; the book must remeasure.

## 2. Why the state set is a set

- **Duplicates must be dropped or the list overflows.** Cox 2007, "Implementation: Simulating the NFA": "Addstate adds a state to the list, but not if it is already on the list. Scanning the entire list for each add would be inefficient; instead the variable listid acts as a list generation number. When addstate adds s to a list, it records listid in s->lastlist. If the two are already equal, then s is already on the list being built." Code: `if(s == NULL || s->lastlist == listid) return; s->lastlist = listid;` and `startlist`/`step` each do `listid++`. — regexp1.html
- **Exponential paths vs. linear states.** Cox 2007: "In an NFA with n nodes, there can only be n reachable states at any step, but there might be 2^n paths through the NFA." (section "Regular Expression Search Algorithms") — regexp1.html
- **Pike VM: dedupe by PC even with captures.** Cox 2009, "Pike's Implementation": "In Pike's VM, the thread state is larger—it includes the saved pointers too—but addthread can still keep just one thread with each possible PC. This is because the saved pointers do not influence future execution: they only record past execution. Two threads with the same PC will execute identically even if they have different saved pointers; thus only one thread per PC needs to be kept." — regexp2.html
- **Python idiom.** UNSOURCED (engineering judgment): the generation counter avoids clearing a visited array in C; in Python a `set` of state ids, or a `dict` keyed by pc for the Pike VM (insertion order doubles as priority order; dicts are ordered since 3.7 — https://docs.python.org/3/library/stdtypes.html#dict, verify wording), does the same job.

## 3. What the NFA approach gives up

- **Backreferences are NP-complete.** Cox 2007, "Real world regular expressions": "Backreferences. As mentioned earlier, no one knows how to implement regular expressions with backreferences efficiently, though no one can prove that it's impossible either. (Specifically, the problem is NP-complete, meaning that if someone did find an efficient implementation, that would be major news to computer scientists and would win a million dollar prize.)" The "NP-complete" link in Cox's page points to Mark Dominus's 3-SAT reduction at http://perl.plover.com/NPC/NPC-3SAT.html, not to Aho. — regexp1.html
- **Aho 1990.** Bibliographic record confirmed: A. V. Aho, "Algorithms for Finding Patterns in Strings", in Handbook of Theoretical Computer Science, Vol. A: Algorithms and Complexity (ed. J. van Leeuwen), 1990, pp. 255–300 — https://dblp.org/rec/books/el/leeuwen90/Aho90.html. UNSOURCED: that this chapter contains the NP-completeness proof for regexes with backreferences (widely attributed, but I could not read the chapter text; the ACM DL page returned 403).
- **Cox's engineering verdict.** "it would be reasonable to use Thompson's NFA simulation for most regular expressions, and only bring out backtracking when it is needed." — regexp1.html
- **Why backreferences break the Pike VM specifically.** Cox 2009, "Real world regular expressions": "Backreferences are trivial in backtracking implementations. In Pike's VM, they can be accommodated, except that the argument about discarding threads with duplicate PCs no longer holds: two threads with the same PC might have different capture sets, and now the capture sets can influence future execution, so an implementation has to keep both threads, a potentially exponential blowup in state." — regexp2.html
- **Captures need thread-carried state (Pike VM), not plain set simulation.** Cox 2009, "Pike's Implementation": "In a 'threaded' implementation like thompsonvm above, we simply add the saved pointer set to the thread state. Rob Pike first used this approach, in the text editor sam." Thread struct: `struct Thread { Inst *pc; char *saved[20]; /* $0 through $9 */ };`. "The case Save code is simpler in pikevm than in recursiveloop, because each thread has its own copy of saved: there is no need to restore the old value." Pike reference: Rob Pike, "The text editor sam," Software—Practice & Experience 17(11), Nov 1987, pp. 813–845. — regexp2.html
- **Cost of captures.** Cox 2010: "The NFA is asymptotically efficient (linear in the size of the regular expression and linear in the size of the input text), but since it must copy around submatch boundary sets, it can be slower in common cases than a backtracker like PCRE. In exchange for guaranteed worst case performance, the average case suffers a little." — https://swtch.com/~rsc/regexp/regexp3.html
- **Lookaround.** Cox 2009 says of "generalized assertions" that they "are harder to accommodate but in principle could be encoded in the NFA" (section "Real world regular expressions", subsection on assertions). RE2's README: "As a matter of principle, RE2 does not support constructs for which only backtracking solutions are known to exist. Thus, backreferences and look-around assertions are not supported." — https://github.com/google/re2/blob/main/README.md
- **Leftmost-first (Perl) vs leftmost-longest (POSIX).** Cox 2009, "Ambiguous Submatching": "Requiring * to be greedy essentially imposes a priority on each thread of execution. We can add such a priority to the VM specification by defining that the split instruction 'prefers' successful execution using its first argument to its second argument." Implementation: "This change ensures that clist and nlist are maintained in order of thread priority, from highest to lowest. ... Because nlist is generated in priority order, the 'ignore a thread if the PC has been seen before' heuristic is safe: the thread seen earlier is higher priority and should be the one that gets saved." And on match cut-off: "if a match is found, threads that occur later in the clist (lower-priority ones) should be cut off, but higher-priority threads need to be given the chance to match possibly-longer sections of the string." — regexp2.html
- **POSIX rule stated.** Cox 2009, "Digression: POSIX Submatching": "POSIX defines that to resolve submatches, first chose the match that starts leftmost in the string. (This is traditional Perl behavior but here things diverge.) Among the submatches starting at the leftmost position in the string, choose the longest one overall." And: "Needless to say, POSIX's rules haven't caught on." — regexp2.html
- **In a DFA/NFA with priorities.** Cox 2010: "In Perl-style rules, the 'leftmost' semantics are handled the same, but Perl doesn't take the longest of the leftmost matches. Instead, the state lists are completely ordered: no two states have equal priority. In an alternation a|b the states exploring a have higher priortiy than the states exploring b." — regexp3.html
- **ECMAScript spec, normative statement of leftmost-first alternation.** "The | regular expression operator separates two alternatives. The pattern first tries to match the left Alternative (followed by the sequel of the regular expression); if it fails, it tries to match the right Disjunction ... Thus, for example, /a|ab/.exec("abc") returns the result "a" and not "ab"." — https://tc39.es/ecma262/multipage/text-processing.html (22.2.2, Note under Disjunction)
- **Perl.** perlre: "Alternatives are tried from left to right, so the first alternative found for which the entire expression matches, is the one that is chosen." and "Normally when a quantified subpattern does not allow the rest of the overall pattern to match, Perl will backtrack." — https://perldoc.perl.org/perlre

## 4. Production engines built on automata

- **RE2 (Google).** README: "RE2 is an efficient, principled regular expression library that has been used in production at Google and many other places since 2006. Safety is RE2's primary goal. ... One of its primary guarantees is that the match time is linear in the length of the input string. It was also written with production concerns in mind: the parser, the compiler and the execution engines limit their memory usage by working within a configurable budget—failing gracefully when exhausted—and they avoid stack overflow by eschewing recursion." Also: "In a sense, RE2 is pessimistic where a backtracking engine is optimistic: A backtracking engine tests each alternative sequentially, making it fast when the first alternative is common. By contrast RE2 evaluates all alternatives in parallel, avoiding the performance penalty for the last alternative, at the cost of some overhead." — https://github.com/google/re2/blob/main/README.md. Syntax wiki marks `\1`, `(?P=name)`, `(?=re)`, `(?!re)`, `(?<=re)`, `(?<!re)`, possessive quantifiers as "NOT SUPPORTED" — https://github.com/google/re2/wiki/Syntax
- **RE2 origin and guarantee.** Cox 2010: "Since Code Search accepts regular expressions from anyone on the Internet, using PCRE would have left it open to easy denial of service attacks." "The result, RE2, provides most of the functionality of PCRE using a C++ interface very close to PCRE's, but it guarantees linear time execution and a fixed stack footprint." — regexp3.html
- **RE2 lazy DFA and cache flush.** Cox 2010: "The RE2 DFA treats its states as a cache; if the cache fills, the DFA frees them all and starts over. This lets the DFA operate in a fixed amount of memory despite considering an arbitrary number of states during the course of the match." Cox 2007 describes the same on-the-fly construction: "the implementation of dstate could choose to throw away the entire DFA so far if the cache grew too large." — regexp3.html; regexp1.html "Caching the NFA to build a DFA"
- **RE2 engine ladder / fallback.** Cox 2010: DFA finds the match location, "then it is time to invoke the NFA to find submatch boundaries"; "A few important common cases don't need the full NFA machinery ... They can be handled with custom code before falling back to the NFA. Use a one-pass NFA if possible." One-pass: "Because there's only one possible next choice, the one-pass NFA implementation never needs to make a copy of the submatch boundary set." Bit-state backtracker for small cases: "In small cases like this one, RE2 uses BitState; in larger cases, it must fall back to NFA." RE2 "disallows PCRE features that cannot be implemented efficiently using automata. (The most notable such feature is backreferences.)" — regexp3.html
- **Go `regexp`.** Package doc: "The regexp implementation provided by this package is guaranteed to run in time linear in the size of the input. (This is a property not guaranteed by most open source implementations of regular expressions.) For more information about this property, see https://swtch.com/~rsc/regexp/regexp1.html or any book about automata theory." Syntax "is the syntax accepted by RE2 and described at https://golang.org/s/re2syntax, except for \C." Default semantics are leftmost-first ("among those it chooses the one that a backtracking search would have found first"); `CompilePOSIX` / `Regexp.Longest` switch to leftmost-longest. — https://pkg.go.dev/regexp (source: https://github.com/golang/go/blob/master/src/regexp/regexp.go)
- **Rust `regex` crate.** Crate docs: "The regex syntax supported by this crate is similar to other regex engines, but it lacks several features that are not known how to implement efficiently. This includes, but is not limited to, look-around and backreferences. In exchange, all regex searches in this crate have worst case O(m * n) time complexity, where m is proportional to the size of the regex and n is proportional to the size of the string being searched." "Untrusted haystacks" section: "The main way this crate guards against searches from taking a long time is by using algorithms that guarantee a O(m * n) worst case time and space bound." Caveat: "the worst case time complexity for iterators is O(m * n^2)" for `find_iter`/`captures_iter`. — https://docs.rs/regex/latest/regex/
- **Rust engines (Gallant, "Regex engine internals as a library", Jul 5, 2023).** PikeVM: "visits each byte in the haystack at most a constant number of times, and it does so by computing all possible active states in lock-step". BoundedBacktracker: "uses additional state to avoid re-tracing steps already taken during backtracking. This allows us to guarantee worst case O(m * n) time, but at the expense of O(m * n) space"; "usually about twice as fast" as PikeVM; fails when "len(regex) * len(haystack) exceeds the configured visited capacity". One-pass DFA: faster still, but construction fails if the regex is not one-pass or exceeds its memory budget. Lazy DFA: "the worst case search time for the lazy DFA is O(m * n) and its worst case space usage is the fixed capacity set at construction time"; "If the cache fills up, it is cleared"; heuristics can make it "return an error if the Cache is being used inefficiently". Full DFA: construction "worst case O(2^m) time". Meta strategy: "Whenever possible, use the lazy DFA (or full DFA if available) to find the overall bounds of the match. If the DFA fails, then we fall back to either the PikeVM, the bounded backtracker or the one-pass DFA. ... Only the PikeVM is required." Semantics: "This is also called leftmost-first matching". — https://burntsushi.net/regex-internals/ (blog.burntsushi.net redirects here)
- **Hyperscan (Intel).** "Hyperscan is a software regular expression matching engine designed with high performance and flexibility in mind." Runtime: "No memory allocations occur at runtime with the exception of two fixed-size allocations" and "There are no internal resource limits or other limitations at runtime that could cause a scan call to return an error." Unsupported: "Backreferences and capturing sub-expressions. Arbitrary zero-width assertions. Subroutine references and recursive patterns. Conditional patterns. Backtracking control verbs. ... Atomic grouping and possessive quantifiers." Semantics differ from Perl: it reports all match ends, e.g. scanning `/foo.*bar/` against `fooxyzbarbar` "will return two matches". No explicit big-O guarantee found in the intro/compilation pages. — https://intel.github.io/hyperscan/dev-reference/intro.html and .../compilation.html

## 5. Which default engines backtrack, which are automata

- **Backtracking:** Perl (perlre, "Perl will backtrack"; Cox 2007 graph); PCRE2 ("The standard algorithm is an 'NFA algorithm'. It conducts a depth-first search of the pattern tree" — https://www.pcre.org/current/doc/html/pcre2matching.html; PCRE2 also ships an alternative `pcre2_dfa_match` that "conducts a breadth-first search of the tree" but cannot do backreferences or captures and "is substantially slower than the standard algorithm"); Python `re` (docs describe possessive quantifiers/atomic groups, 3.11+, in terms of the engine being "backtracked" and of "stack points" — https://docs.python.org/3/library/re.html; Cox 2007 measured Python on the backtracking curve); Java `java.util.regex` ("The Pattern engine performs traditional NFA-based matching with ordered alternation as occurs in Perl 5." — https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/regex/Pattern.html; Cox 2007: "the java.util.regex interface requires a backtracking implementation, because arbitrary Java code can be substituted into the matching path"); JavaScript (ECMA-262 pattern semantics are defined via backtracking continuations: "Due to backtracking, many MatchStates may be in use at any time during the matching process." — tc39.es link above). Note the terminology trap: PCRE and Java call backtracking "NFA-based"; Cox and Gallant call it "the 'NFA algorithm'" in scare quotes.
- **Automata:** RE2, Go `regexp`, Rust `regex` (citations in section 4). GNU grep/awk build DFAs (Cox 2007).
- **Hybrids:** .NET 7 added `RegexOptions.NonBacktracking`, "with an implementation grounded in the Symbolic Regex Matcher work from Microsoft Research (MSR)". Toub's example: "The processing is now effectively linear in the length of the (short) input." Implementation: "starts with a DFA, building out the nodes lazily, and at some point if the graph gets too big, it switches over dynamically to NFA-based processing". Unsupported: "Atomic groups, Backreferences, Balancing groups, Conditional, Lookarounds, Start anchors (\G)" and cannot combine with RightToLeft or ECMAScript. "Note that the goal of NonBacktracking is not to be always faster than the backtracking engines." — Stephen Toub, "Regular Expression Improvements in .NET 7", May 12, 2022, https://devblogs.microsoft.com/dotnet/regular-expression-improvements-in-dotnet-7/. Rust's BoundedBacktracker and RE2's BitState are the reverse hybrid: backtracking with a visited bitmap, so still O(m·n) (section 4). GNU grep, per Cox 2009, "rewrites backreferences into an approximate regular expression that can be used with a DFA" then checks candidates with a backtracker.

## 6. Benchmarking methodology in Python

- **Clock.** `time.perf_counter()`: "a clock with the highest available resolution to measure a short duration. It does include time elapsed during sleep. ... The reference point of the returned value is undefined, so that only the difference between the results of two calls is valid." — https://docs.python.org/3/library/time.html#time.perf_counter. `timeit`'s default timer is `time.perf_counter()` (changed in 3.3). — https://docs.python.org/3/library/timeit.html
- **Take the minimum.** `Timer.repeat` note: "It's tempting to calculate mean and standard deviation from the result vector and report these. However, this is not very useful. In a typical case, the lowest value gives a lower bound for how fast your machine can run the given code snippet; higher values in the result vector are typically not caused by variability in Python's speed, but by other processes interfering with your timing accuracy. So the min() of the result is probably the only number you should be interested in." — timeit docs
- **Defaults and GC.** Default `number` is 1,000,000 and default `repeat` is 5 (changed from 3 in 3.7). "By default, timeit() temporarily turns off garbage collection during the timing. The advantage of this approach is that it makes independent timings more comparable. The disadvantage is that GC may be an important component of the performance of the function being measured." `Timer.autorange()` "calls timeit() repeatedly so that the total time >= 0.2 second". — timeit docs
- **Warm-up, machine, input size.** UNSOURCED beyond the timeit rationale: repeating and discarding a first run, and stating Python version, CPU, OS and n for every number. The book policy is: print only numbers the book's own scripts measured on the stated machine; never reuse Cox's 2007 figures as if current. For exponential-vs-linear demonstrations use small n (Cox: backtracking "will not scale much beyond n=25"; PCRE's step limit bites at n=23) and a wall-clock cap.
- **Caveat on Python `re` comparisons.** Python 3.11+ has possessive quantifiers and atomic groups, so `re` can sometimes be told to avoid catastrophic backtracking; the book's `a?^n a^n` demo has no such escape hatch (no backreference either), so it is a fair like-for-like input.

## 7. Differential testing

- **RE2's own approach (exhaustive small-case cross-checking).** Cox 2010, "Testing": "Given a list of small regular expressions and operators, the RegexpGenerator class generates all possible expressions using those operators up to a given size. Then the StringGenerator generates all possible strings over a given alphabet up to a given size. Then, for every regular expression and every input string, the RE2 tests check that the output of the four different regular expression engines agree with each other, and with a trivial backtracking implementation written only for testing, and (usually) with PCRE itself." "The exhaustive tests must limit themselves to small regular expressions and small input strings, but most bugs can be exposed by small test cases." This is the model for `tinyre` vs `re`: enumerate small patterns over a tiny alphabet, enumerate short strings, compare. — regexp3.html
- **Rust regex: one TOML suite, every engine.** testdata README: the directory holds "a large suite of regex tests defined in a TOML format. They are used to drive tests in tests/lib.rs, regex-automata/tests/lib.rs and regex-lite/tests/lib.rs", so "one set of tests" runs "on every engine". — https://github.com/rust-lang/regex/blob/master/testdata/README.md; format documented at https://docs.rs/regex-test ("A crate for defining tests in a TOML format and applying them to regex engine implementations"). Gallant's blog explains the motivation: "you really want to leverage the same tests across all of the engines". Fuzz targets present in the repo: ast_fuzz_match, ast_fuzz_match_bytes, ast_fuzz_regex, ast_roundtrip, fuzz_regex_automata_deserialize_dense_dfa, fuzz_regex_automata_deserialize_sparse_dfa, fuzz_regex_lite_match, fuzz_regex_match — https://github.com/rust-lang/regex/tree/master/fuzz/fuzz_targets
- **Practitioner report.** "Ring Around The Regex: Lessons learned from fuzzing regex libraries (Part 1)", addison, secret.club, Jun 30, 2024: "I've even made differential fuzzers which have had success in identifying some consistency bugs between versions and sub-implementations." — https://secret.club/2024/06/30/ring-around-the-regex-1.html
- **Academic framing and the dialect caveat.** Çakar, Lee, Davis, "Towards the Systematic Testing of Regular Expression Engines", arXiv 2603.00311 (Feb 27, 2026): "A common strategy for testing regex engines involves differential testing -- comparing outputs across different implementations. However, this approach is concerning because regex syntax and semantics vary significantly between dialects (e.g., POSIX vs. PCRE). Fuzzing is also utilized ... but naive byte-level mutations generate syntactically invalid inputs that exercise only parsing logic, not matching internals." They "surveyed testing practices across 22 regex engines". Lesson for the book: `tinyre` deliberately implements a strict subset of Python `re` syntax with the same leftmost-first semantics, so the dialect problem is avoided by construction; generate patterns from `tinyre`'s own grammar, not by byte mutation. — https://arxiv.org/abs/2603.00311
- **Hypothesis.** "Hypothesis is the property-based testing library for Python. With Hypothesis, you write tests which should pass for all inputs in whatever range you describe, and let Hypothesis randomly choose which of those inputs to check - including edge cases you might not have thought about." — https://hypothesis.readthedocs.io/en/latest/. `hypothesis.strategies.from_regex(regex, *, fullmatch=False, alphabet=None)` "Generates strings that contain a match for the given regex (i.e. ones for which re.search() will return a non-None result)." — https://hypothesis.readthedocs.io/en/latest/reference/strategies.html. Book dependency policy prefers the standard library: show the differential test with `random` + `itertools.product` (RE2-style enumeration) and mention Hypothesis in one sidebar as the off-the-shelf option.
