# Research notes: backtracking matchers and catastrophic backtracking

Researcher notes for *A Regex Engine From Scratch*. Format: `claim — source — quote/page ref`. Anything marked **UNSOURCED** must not be used as fact. Access date for all URLs: 2026-09-05.

## 1. Lineage of the tiny recursive matcher (Pike / Kernighan) and grep's origin

**Provenance.** The matcher first appeared in Kernighan & Pike, *The Practice of Programming* (Addison-Wesley, 1999, ISBN 0-201-61586-X), chapter 9 "Notation", section 9.2 "Regular Expressions" — https://www.cs.princeton.edu/~bwk/tpop.webpage/ and https://www.cs.princeton.edu/~bwk/tpop.webpage/toc.html (TOC lists ch. 9 "Notation", 9.2 "Regular Expressions"). Kernighan retold its story as chapter 1, "A Regular Expression Matcher", of *Beautiful Code* (eds. Andy Oram & Greg Wilson, O'Reilly, 2007, ISBN 9780596510046) — O'Reilly TOC: https://www.oreilly.com/library/view/beautiful-code/9780596510046/ch01.html. Kernighan's chapter is posted in full at Princeton: https://www.cs.princeton.edu/courses/archive/spr09/cos333/beautiful.html (all quotes below are from that page).

**Why it was written / how long.** "The problem was that any existing regular expression package was far too big. The local grep was over 500 lines long ... none was remotely suitable for pedagogy." / "Rob disappeared into his office, and at least as I remember it now, appeared again in no more than an hour or two with the 30 lines of C code that subsequently appeared in Chapter 9 of TPOP." Pike's own account: "I didn't have a design when I started, I just began to code and saw what developed. Suddenly, I was done." Note Kernighan hedges with "at least as I remember it now" — preserve the hedge.

**Subset handled** (verbatim list): `c` any literal character; `.` any single character; `^` beginning of the input string; `$` end of the input string; `*` zero or more occurrences of the previous character. Kernighan: "This is quite a useful class; in my own experience of using regular expressions on a day-to-day basis, it easily accounts for 95 percent of all instances." (Personal experience claim, not a measurement.)

**Structure.** Three functions. `match` handles the `^` anchor, otherwise loops calling `matchhere` at every start position (comment: "must look even if string is empty" — the `do/while` runs once for empty text). `matchhere` is the recursive core: empty pattern matches; if `regexp[1]=='*'` delegate to `matchstar(regexp[0], regexp+2, text)`; `$` at end of pattern matches only end of text; otherwise consume one character if it is `.` or equals the text char, and recurse on `regexp+1, text+1`. `matchstar` loops: "a * matches zero or more instances" — try `matchhere(regexp, text)`, then advance one text char while it equals `c` (or `c=='.'`). Full code is on the Princeton page; the writer can reproduce it (short, Kernighan published it for teaching).

**`*` semantics and its limits.** "The function matchstar(c, regexp, text) tries to match repetitions of the text character c, beginning with zero repetitions and counting up, until it either finds a match of the rest of the text, or it fails ... This identifies a 'shortest match', which is fine for simple pattern matching as in grep." I.e. this `*` is lazy, not greedy, and `*` applies only to a single character or `.`, not to groups (no parentheses, no `|`, no `+`). Also: "If there are multiple matches, only the first (leftmost) one will be identified." Kernighan on cost: "If a pattern includes several .*s, the straightforward implementation requires a lot of backtracking, and in some cases will run very slowly indeed. (The standard Unix grep has the same properties.) For example, the command grep 'a.*a.*a.*a.a' takes about 20 seconds to process a 4 MB text file on a typical machine." (Conditions: 2007-era machine, unspecified; treat the 20 s as anecdote.)

**Why it is short / beautiful.** "First, the features are well chosen to be the most useful ... without any frills." / "Recursion is a win. This fundamental programming technique almost always leads to smaller, cleaner and more elegant code." / "The recursion is not only the implementation method, it's also a reflection of the thought process taken when writing the code."

**grep and Thompson.** Thompson, K. "Programming Techniques: Regular expression search algorithm", *Communications of the ACM* 11(6):419–422, June 1968, doi:10.1145/363347.363387 (bibliographic data from Semantic Scholar API; text read from https://www.oilshell.org/archive/Thompson-1968.pdf, 4 pp.). Abstract: "The compiler accepts a regular expression as source language and produces an IBM 7094 program as object language." Key sentence contrasting with backtracking, p. 419: "Previous search algorithms involve backtracking when a partially successful search path fails. This necessitates a lot of storage and bookkeeping, and executes slowly. In the regular expression recognition technique described in this paper, each character in the text to be searched is examined in sequence against a list of all possible current characters. During this examination a new list of all possible next characters is built." And: "This compile-search algorithm is incorporated as the context search in a time-sharing text editor" (QED on CTSS, per Cox regexp1). grep's birth — McIlroy, *A Research UNIX Reader* (Bell Labs CSTR 139, 1987), https://www.cs.dartmouth.edu/~doug/reader.pdf, section "GREP (v4 page 24)": "Grep, generally cited as the prototypical software tool, was born when Ken Thompson was asked how to search for patterns in a file that was too big for the editor. Thompson promptly liberated his regular expression recognizer and christened it after the ed command g/re/p. It was an instant hit and soon entered our language as a verb." Also "Grep (Thompson, v4) ingrained the tools outlook irrevocably." Cox (regexp1, paraphrase from my read) says that when Thompson wrote `ed` for Unix in 1971 he used recursive backtracking rather than his 1968 algorithm; the writer should re-check that sentence on swtch.com before quoting it.

## 2. Catastrophic backtracking / ReDoS: mechanism and documented incidents

**Mechanism (Cox).** Russ Cox, "Regular Expression Matching Can Be Simple And Fast", Jan 2007, https://swtch.com/~rsc/regexp/regexp1.html. On `a?^n a^n` against `a^n`: "There are n such choices to make, a total of 2^n possibilities. Only the very last possibility—choosing zero for all the ?—will lead to a match. The backtracking approach thus requires O(2^n) time." Measured: "Perl requires over sixty seconds to match a 29-character string. The other approach, labeled Thompson NFA ... requires twenty microseconds." "Perl, PCRE, Python, and Ruby are all using recursive backtracking"; Java too. Cox also notes PCRE "stops getting the right answer at n=23, because it aborts the recursive backtracking after a maximum number of steps" (so PCRE has a step limit, CPython `re` does not appear to; see §3). Cox on real-world frequency: pathological expressions are rare but "less dramatic ones do occur". Perl's memoization "requires a memory footprint roughly equal to the size of the text times the size of the regular expression."

**Mechanism (OWASP, Davis).** OWASP "Regular expression Denial of Service - ReDoS" (author Adar Weidman), https://owasp.org/www-community/attacks/Regular_expression_Denial_of_Service_-_ReDoS: an "Evil Regex" has "Grouping with repetition" and, inside the group, "Repetition" or "Alternation with overlapping"; examples `(a+)+$`, `([a-zA-Z]+)*$`, `(a|aa)+$`, `(a|a?)+$`; worked example `^(a+)+$` on 16 a's + `X` → 65,536 paths. Cites Crosby & Wallach (USENIX Security 2003) as origin of the ReDoS idea. Davis, Coghlan, Servant, Lee, "The Impact of Regular Expression Denial of Service (ReDoS) in Practice", ESEC/FSE 2018, doi:10.1145/3236024.3236027, PDF https://davisjam.github.io/files/publications/DavisCoghlanServantLee-EcosystemREDOS-ESECFSE18.pdf: "SL behavior is also known as catastrophic backtracking." Three anti-patterns: (1) "star height > 1, i.e., nested quantifiers ... as is the case for the string 'a' in the regex /(a+)+/ ... worst-case exponential behavior on a mismatch"; (2) "Quantified Overlapping Disjunction (QOD) ... /(\w|\d)+/ ... worst-case exponential"; (3) "Quantified Overlapping Adjacency (QOA) ... /\s*\.#\s*$/ ... worst-case polynomial behavior on a mismatch." Prevalence (conditions: 375,652 npm + 72,750 pypi modules cloned, 2018): "about 1% of all unique regexes in both npm and pypi were SL regexes"; "Exponential SL regexes were rare in both registries: only 7% of the SL regexes from npm and 6% of those from pypi were exponential. The majority ... were polynomial, tending to O(n^2) and O(n^3)." Also: "in npm 12% of the SL regexes had star height > 1, but 94% of the regexes with star height > 1 were linear-time" — nested quantifiers are a necessary-ish signal, not sufficient. Engines: "many popular languages, including JavaScript-V8 (Node.js), Python, Java, C++-11, C#-Mono, PHP, Perl, and Ruby, rely on a regex engine with worst-case super-linear behavior".

**Incident: Cloudflare, 2019-07-02.** John Graham-Cumming, "Details of the Cloudflare outage on July 2, 2019", https://blog.cloudflare.com/details-of-the-cloudflare-outage-on-july-2-2019/. WAF rule deployed 13:42 UTC; global WAF kill 14:07; normal by 14:09; ~27 min. Regex: `(?:(?:\"|'|\]|\}|\\|\d|(?:nan|infinity|true|false|null|undefined|symbol|math)|\`|\-|\+)+[)]*;?((?:\s|-|~|!|{}|\|\||\+)*.*(?:.*=.*)))`; culprit `.*(?:.*=.*)`; "we can safely ignore it and treat the pattern as `.*.*=.*`". Step counts (from Perl Regexp::Debugger): `x=x` 23 steps, `x=xx` 33, `x=xxx` 45, `x=` + 20 x's 555; with trailing `;` (`.*.*=.*;`, no match): `x=x` 90, 20 x's 5,353. Post's own wording: "That's not linear." **The post never says "exponential", "quadratic" or "polynomial"** (I searched the text). The numbers are consistent with quadratic growth (555/23 ≈ 24 for n from 1 to 20; see §4 measurements). Fix: re-introduce the CPU-time limit that "was removed by mistake during a refactoring"; move to "re2 or Rust regex engine which both have run-time guarantees". Post cites Thompson 1968: "The solution to this problem has been known since 1968 when Ken Thompson wrote a paper ... executes in time linear in the size of the string." Engine at the time: Lua + PCRE.

**Incident: Stack Overflow, 2016-07-20.** "Outage Postmortem - July 20, 2016", Stack Exchange Network Status, posted 2016-07-20 20:47, https://stackstatus.net/post/147710624694/outage-postmortem-july-20-2016 (I read it at the mirror https://stackstatus.tumblr.com/post/147710624694/outage-postmortem-july-20-2016; stackstatus.net sits behind a JS challenge). "34 minute outage starting at 14:44 UTC. It took 10 minutes to identify the cause, 14 minutes to write the code to fix it, and 10 minutes to roll out the fix." Regex `^[\s\u200c]+|[\s\u200c]+$` "intended to trim unicode space from start and end of a line"; simplified `\s+$`. Trigger: "roughly 20,000 consecutive characters of whitespace on a comment line". Cost: "20,000+19,999+19,998+…+3+2+1 = 199,990,000 times". Crucially, in their own words: "This is not classic catastrophic backtracking ... (performance is O(n²), not exponential, in length), but it was enough." Fix: "replaced with a substring function." Outage amplified because the home page was the load-balancer health check. (Engine: .NET; UNSOURCED beyond common knowledge that Stack Overflow ran on .NET — the post does not name the engine.)

**Other incidents.** Davis 2018 cites the 2016 Express.js vulnerability ([17] in the paper) alongside Stack Overflow; I did not locate a primary post-mortem for it. UNSOURCED: various blog posts attribute other outages (e.g. "CrowdStrike 2024 was regex") — no primary source found; do not use.

## 3. Python's `re`

**Engine type.** CPython's `re` is Fredrik Lundh's SRE, a backtracking engine: `Modules/_sre/sre_lib.h` header "Secret Labs' Regular Expression Engine ... Copyright (c) 1997-2001 by Secret Labs AB", and comment in the REPEAT_ONE handler: "check if the rest of the pattern matches, and backtrack if not" — https://raw.githubusercontent.com/python/cpython/main/Modules/_sre/sre_lib.h. The library reference never calls it a "backtracking engine" outright; the HOWTO does describe it behaviourally: "when repeating a RE, the matching engine will try to repeat it as many times as possible. If later portions of the pattern don't match, the matching engine will then back up and try again with fewer repetitions" and "the regular expression engine has to backtrack character by character" — https://docs.python.org/3/howto/regex.html. Cox 2007 lists Python among recursive-backtracking implementations (§2).

**Protection.** The `re` docs (https://docs.python.org/3/library/re.html) mention no timeout, step limit, or ReDoS warning (searched). My experiment (§4) ran `(a+)+b` unbounded to n=26 without error, consistent with no step limit. **UNSOURCED** as a documented guarantee: "CPython `re` has no backtracking limit" — state as observation, not doc fact.

**Mitigations added in 3.11.** What's New 3.11: "Atomic grouping ((?>...)) and possessive quantifiers (*+, ++, ?+, {m,n}+) are now supported in regular expressions. (Contributed by Jeffrey C. Jacobs and Serhiy Storchaka in bpo-433030.)" — https://docs.python.org/3/whatsnew/3.11.html. Library reference wording: possessive quantifiers "do not allow back-tracking when the expression following it fails to match"; `x*+` "equivalent to `(?>x*)`"; atomic group: "the stack can only be unwound to a point *before* the (?>...) because once exited, the expression ... has thrown away all stack points within itself"; example "(?>.*). would never match anything". Each entry says "Added in version 3.11."

**`regex` third-party module.** https://pypi.org/project/regex/ (version 2026.9.3 shown, released 2026-09-01): "The matching methods and functions support timeouts. The timeout (in seconds) applies to the entire operation"; raises `TimeoutError` ("regex timed out"). Also supports atomic groups and possessive quantifiers.

## 4. Measuring blow-up honestly in Python

**What is exponential and what is not.** Exponential (2^n-ish) requires a *nested* or *overlapping* quantifier whose inner choices multiply per input character: `(a+)+b`, `(a*)*b`, `(a|aa)+$`, Cox's `a?^n a^n`. Two adjacent overlapping quantifiers (`.*.*=`, `\s+\s+`, `\s+$` under `search`) are *polynomial*: n^2 (or n^3 with an unanchored search that retries every start). Both Cloudflare (`.*.*=.*`) and Stack Overflow (`\s+$`) were polynomial, and Stack Overflow said so explicitly (§2). So "cost doubles per character" is correct only for the nested-quantifier family; for `.*.*=.*` cost roughly *quadruples per doubling of input*.

**Method.** `time.perf_counter()` around a single `pattern.fullmatch(s)` (anchored, so the measurement isn't polluted by `search`'s start-position loop), double n (or add one character for the exponential case), report the ratio. Krishnan Chandra's write-up shows the same method with `perf_counter_ns` and log-log plots, plus `py-spy dump` to catch a live process stuck in `re.search` — https://krishnanchandra.com/posts/regex-catastrophic-backtracking/ (2023-09-05). Jan Goyvaerts' RegexBuddy step counts for `(x+x+)+y`: 10 x's 2557 steps, 11 → 5117, 12 → 10237 (≈ ×2 per char) — https://www.regular-expressions.info/catastrophic.html.

**My measurements** (CPython 3.14.7, macOS, single run each, wall clock; writer should re-run and quote their own numbers):

| pattern / call | input | growth observed |
|---|---|---|
| `(a+)+b` fullmatch | `'a'*n`, no `b` | ×1.9–2.0 per extra char; n=20 0.030 s, n=24 0.48 s, n=26 1.92 s |
| `(a+)+b` search | same | same doubling, ~2× the fullmatch time |
| `(a+)+b` fullmatch | `'a'*n+'b'` (succeeds) | ~0 s even at n=10,000 (blow-up needs a *failing* match) |
| `(a|aa)+$` match | `'a'*n+'!'` | ×6.9 per +4 chars ≈ ×1.62/char (Fibonacci-many parses); n=36 1.9 s, n=40 13 s |
| `.*.*=.*;` match | `'x='+'x'*n` | ×3.4–4.0 per doubling (quadratic); n=8000 0.021 s |
| `.*.*=.*;` search | same | ×7–7.6 per doubling (cubic); n=1600 0.47 s |
| `\s+$` search | `' '*n+'x'` | ×4.0 per doubling (quadratic); n=20,000 0.94 s, n=40,000 3.8 s |
| `a*a*b` fullmatch | `'a'*n` | ×4 per doubling (quadratic) |
| `a*b` fullmatch | `'a'*n` | ×2 per doubling (linear); n=800,000 0.6 ms |
| `(?>(a+)+)b`, `(a++)+b`, `(?>a+)+b` fullmatch | `'a'*24` | <0.01 ms vs 0.48 s for `(a+)+b` |

Note `\s+$` at 20,000 spaces took ~1 s here; Stack Overflow's ~200 M checks per home-page render, on every request, is what made it an outage.

## 5. Teaching implementations worth pointing to

- Kernighan's chapter text + C code (primary) — https://www.cs.princeton.edu/courses/archive/spr09/cos333/beautiful.html.
- Ben Hoyt, "Rob Pike's simple C regex matcher in Go" (Aug 2022) — https://benhoyt.com/writings/rob-pike-regex/ — line-by-line Go port, benchmarks, notes `a.*a.*a.*a.a`-style patterns have "horrible run times" and neither version handles Unicode.
- Greg Wilson, *Software Design by Example* (Python), ch. "Matching Patterns" — https://third-bit.com/sdxpy/glob/ — object-per-operator recursive backtracking matcher (literal, `*`, `{a,b}` alternatives) where each matcher's `_match` returns the position to continue from; closest Python analogue of Pike's design.
- lorenzofelletti/pyregex — https://github.com/lorenzofelletti/pyregex — Python backtracking engine with lexer, recursive-descent parser and engine; supports classes, groups, alternation, `{n,m}`; no ReDoS discussion.
- Marcin Chwedczuk, "Matching regexes using backtracking" (blog host unreachable on 2026-09-05; code at https://github.com/marcin-chwedczuk/reng, Java) — AST + continuation-passing backtracker; search snippet says it discusses `(a+)*c` blow-up.
- xysun/regex — https://github.com/xysun/regex — Python Thompson-NFA engine; benchmark vs `re` shows it loses on normal inputs, wins on pathological ones (the natural "next chapter" contrast).
- Carl Friedrich Bolz-Tereick, "An Efficient and Elegant Regular Expression Matcher in Python" (PyPy blog, 2010-05-21) — https://morepypy.blogspot.com/2010/05/efficient-and-elegant-regular.html — Fischer/Huch/Wilke marking algorithm, O(m·n), no backtracking; notes it "could not be used to implement PyPy's re module" because `re` semantics need backtracking.
- Russ Cox's series index — https://swtch.com/~rsc/regexp/ — regexp1 (2007), regexp2 "the virtual machine approach" (Dec 2009), regexp3 (RE2).
