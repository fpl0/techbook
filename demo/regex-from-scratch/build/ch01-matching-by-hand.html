Chapter 1: Matching by Hand

Here is a regular expression that will hang your program. Not for a long time. Forever, on a modern machine, for an input of about thirty characters.

Output
True

That one returns quickly. Remove the final b so the match must fail, and Python's engine explores every way of splitting the as between the inner and outer group before it gives up. Each additional a doubles the work.

What you'll learn

  • Match a small regex language by hand, with nothing but recursion
  • Explain why backtracking engines have a worst case that is exponential
  • Read a regex as a structure rather than as a string of punctuation

Assumes you know

Python functions, recursion, and slicing. No automata theory. That arrives in chapter 2, once you have felt why it is needed.

~25 min · 4 exercises

The smallest language worth building#

Real regex syntax is enormous, and almost none of it is interesting. We will implement four constructs, which is enough to be genuinely useful and small enough to hold in your head:

SyntaxMeaning
athe literal character a
.any single character
abconcatenation: a then b
a*zero or more a

No alternation yet, no +, no character classes. We add alternation in chapter 2, where it costs almost nothing; here it would double the code for one idea.

Matching, recursively#

The whole matcher is one insight: match(pattern, text) asks whether the pattern consumes some prefix of the text, and the pattern's first element decides what to try next.

Start with the case that has no star in it.

Output
True True False
  1. An empty pattern matches anything, including the empty string. This is the base case, and getting it wrong is the most common bug in a first attempt.
  2. text and guards the index: a pattern that still has characters left cannot match text that has run out.
  3. Both branches recurse on both tails, because one pattern element consumed exactly one text character.
Predict: what does match_here("", "abc") return, and is that right?

True. The empty pattern matched the empty prefix of "abc" and stopped. That is correct for a prefix matcher, which is what we are building. It answers "does this pattern start here?", not "does it consume everything?". Anchoring to the end is exercise 3.

Adding the star#

a* is where the difficulty lives, because it is the first construct that does not consume a fixed amount of text. The pattern element is now two characters wide, and it can match any number of characters from zero upward.

The standard move is to try every count. Try zero first, then one, then two, and return as soon as one of them works.

Output
'a*b'    'aaab'   True
'a*b'    'b'      True
'a.*z'   'abcz'   True
'a*b'    'aaac'   False

Note the order inside match_star: it tries the shortest match first, growing only when the rest of the pattern fails. That makes this a lazy matcher. Real engines are greedy by default, which changes which match you get but not whether one exists.

This trips people up

match_star checks match_here(pattern, ...), the pattern after the star, not including it. Passing the full pattern is the classic error, and it produces infinite recursion rather than a wrong answer, which at least fails loudly.

Why this gets slow#

The matcher above is correct and short. It is also, on some inputs, unusable.

Consider a*a*a*b against a string of as with no b. Every a in the text can be claimed by the first star, the second, or the third. The matcher tries every assignment before it can conclude failure.

Measure it rather than trusting the claim. The block below doubles the input twice and prints the cost each time.

Output
n= 10       0.20 ms
n= 20       1.90 ms
n= 40      22.57 ms
n= 60     104.08 ms

Doubling the input from 20 to 40 does not double the time; it multiplies it by roughly twelve. That is the signature of a polynomial with a degree above one. Add a fourth star and the same doubling costs about twenty times more, because the degree of the polynomial is set by how many stars can compete for the same character, not by the length of the input.

Our four-construct language cannot do worse than polynomial, because it has no way to nest one repetition inside another. Real regex syntax can, and that is where the genuinely exponential case lives: the (a+)+b from the opening of this chapter. The outer + repeats a group that itself repeats, so the number of paths doubles with each added character rather than growing polynomially. Cloudflare's global outage of 2 July 2019 was caused by a single regular expression containing nested quantifiers, deployed to their WAF. It consumed CPU across the fleet.

Both failures share one cause: the matcher explores one candidate division at a time and, on failure, starts another. Nesting changes how fast the path count grows. It does not introduce the problem.

Practice#

Exercise

Fill the single blank so match_here also supports ? (zero or one).

Solution

match_here(pattern[2:], text). The zero-occurrence branch is the one you want. Order matters: trying the one-occurrence branch first makes ? greedy, which is what every real engine does.

Exercise

Add ^ anchoring. Complete the stub.

Solution

match_here(pattern[1:], text). An anchored pattern tries position zero only, which is why anchoring a slow pattern often makes it fast. It removes the outer loop over starting positions, though not the inner exponential blowup.

Exercise

Write full_match(pattern, text) from scratch: true only if the pattern consumes the entire text. Do not modify match_here.

Exercise

Transfer: unmemoized recursive Fibonacci has the same shape as (a+)+, and counting coin-change combinations has the same shape as a*a*a*. Say in one sentence what distinguishes the two shapes, before reading chapter 2.

What to remember#

  • A pattern element decides what to try next; matching is recursion over both the pattern and the text
  • An empty pattern matches successfully, and that base case carries the whole recursion
  • The star case tries every repetition count, and that is where the cost lives
  • Stars competing for the same characters give polynomial cost, with the degree set by how many compete
  • Nested repetition, which our language cannot express, is what makes the cost exponential
  • Both are properties of the search strategy, not of regular expressions themselves

Terms introduced: backtracking, anchoring, greedy and lazy matching, nested quantifier, catastrophic backtracking.
